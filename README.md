# pms-platform-scaling

[![ci](https://github.com/manojrevenkar12-web/pms-platform-scaling/actions/workflows/ci.yml/badge.svg)](https://github.com/manojrevenkar12-web/pms-platform-scaling/actions/workflows/ci.yml)

The write path of a hotel property-management system, made to scale out, and the tooling to
move its legacy infrastructure from CloudFormation to Terraform without touching a resource.

Three problems, each measured on real PostgreSQL servers rather than mocked:

1. **Writes outgrow one primary.** Accounts (hotel groups) are sharded across PostgreSQL
   primaries. A fenced router sends each transaction to the account's shard, and an account can
   be **moved to another shard while it keeps taking bookings**: logical replication with a
   per-account row filter, a freeze that cannot be starved, a checksum, a directory flip.
2. **Hot rows.** Every booking for a popular night decrements the same availability counter. The
   counter is split into slots taken with `SKIP LOCKED`: twice the throughput on a hot night,
   with no oversell and no false "sold out".
3. **Infrastructure in two tools.** `cfn2tf` turns a deployed CloudFormation stack into Terraform
   with import blocks, a retain template and a handover plan, and checks the resulting Terraform
   plan. CI deploys a stack with CloudFormation (LocalStack), hands it over, and proves that the
   plan only imports and that nothing changes after the import.

## Results

From [reports/BENCHMARK.md](reports/BENCHMARK.md) (generated by `go run ./cmd/bench`; one
2-CPU machine, durable commits, PostgreSQL 16):

| What | Result |
|---|---|
| Accounts moved while writing (10 moves, 8 accounts writing) | 39,002 acknowledged writes, **0 lost, 0 duplicated, 0 failed** |
| Write pause of the moving account | p50 205 ms, max 546 ms; other accounts never paused |
| Pause without load, by account size | ~20 ms without checksum; with checksum 43 ms (2k reservations) to 688 ms (100k) |
| Hot night, 16 writers: 1 slot vs 16 slots | 872 vs 1,717 bookings/s; p99 80 vs 21 ms |
| Sell-out races (400 rooms, 400 or 1,600 requests at once) | exactly 400 sold every time, 0 left |
| Stack handover (11 CloudFormation resources → 17 Terraform resources, LocalStack) | **17 imported, 0 real changes** (1 equivalent JSON rewrite: LocalStack returns a redrive policy with other whitespace); no changes after apply; the stack retains every resource |

These numbers show behaviour (contention, pauses, correctness). All servers share one small
machine, so they are not the capacity of a production cluster; capacity scaling with shard count
needs shards on separate machines and is not measured here.

## How a move works

```
source shard                 control database           target shard
-----------------------------------------------------------------------------------------
CREATE PUBLICATION ... WHERE (account_id = 'acc')
                                                        CREATE SUBSCRIPTION (copy + stream)
                                                        wait: all tables synced, WAL caught up
fence lock (exclusive) + frozen = true   -- writers of 'acc' now wait; nobody else does
                                                        wait: the freeze row has arrived
checksum(acc) ========================================= checksum(acc)
                             tenants.shard = target,
                             epoch + 1
                                                        DROP SUBSCRIPTION; frozen = false
moved_to = target; DROP PUBLICATION                     -- writers resume here
delete acc's rows (tombstone fence row stays)
```

Writers take the account's fence lock shared and read its fence row on the shard in every
transaction, so a stale directory cache costs a retry, never a write on the wrong shard
(`TestStaleRouterFollowsTheMove`). The freeze uses an advisory lock because PostgreSQL queues
those: a writer arriving after the freeze waits behind it, so a busy account cannot starve its
own move. Every step is recorded in the control database; a crashed mover is run again and
resumes (`TestMoveResumesAfterCrash` crashes it after each step under load). A mismatch after
the freeze aborts the move and the account keeps working on the source
(`TestMismatchAbortsTheMove`).

## Layout

```
cmd/pms-api        HTTP API: book, cancel, availability, inventory; /metrics, /healthz, /readyz
cmd/reshard        init shards, place accounts, move, abort, status
cmd/bench          the benchmark; writes reports/
cmd/cfn2tf         CloudFormation stack -> Terraform + imports + HANDOVER.md
internal/router    fenced routing with retries (moving, stale route, deadlock, serialization)
internal/mover     the online move state machine
internal/booking   slot-based availability, idempotent bookings, cancellations, inventory
internal/directory account -> shard map with a cache
internal/cfn       CloudFormation template parser (YAML short tags and JSON)
internal/cfn2tf    conversion, HCL writer, handover plan
internal/metrics   Prometheus text format, no dependencies
internal/pgtest    starts real PostgreSQL servers for tests and the benchmark
config/            settings (platform.yaml)
examples/          the legacy CloudFormation stack used in CI
scripts/           handover-e2e.sh (LocalStack)
```

## Run it

Needs Go 1.24 and PostgreSQL 15+ server binaries (`PG_BIN`, default
`/usr/lib/postgresql/16/bin`). Tests start their own servers with logical replication on.

```
go test ./...                          # unit and integration tests (real PostgreSQL)
go run ./cmd/bench -quick              # the benchmark, short
scripts/handover-e2e.sh                # needs LocalStack on :4566, terraform, aws CLI
```

Against your own servers:

```
reshard init  -control "$PMS_CONTROL_DSN" -shard-dsn shard-0="$SHARD0" -shard-dsn shard-1="$SHARD1"
reshard place -control "$PMS_CONTROL_DSN" -account acc-1 -shard shard-0
pms-api -control "$PMS_CONTROL_DSN"    # settings in config/platform.yaml
reshard move  -control "$PMS_CONTROL_DSN" -account acc-1 -to shard-1
```

API keys in `config/platform.yaml` are stored as SHA-256 digests, one account each. In a real
deployment the identity provider sits in front and passes the verified account instead.

## Not done here

- Shards on separate machines and capacity numbers per shard count.
- A read model for cross-account queries.
- Schema migrations across shards (they would run shard by shard, recorded in the control database).
- The real AWS account: the handover is proved against LocalStack, whose CloudFormation skips
  lifecycle rules, log retention and `DeletionPolicy` on delete (the e2e applies the first two
  through the APIs and does not delete the stack; see [ADR 3](docs/adr/0003-cloudformation-to-terraform.md)).
  Run the plan step against AWS before a production handover.
